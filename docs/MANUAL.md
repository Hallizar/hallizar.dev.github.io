# 📘 Руководство: использование, модерация и деплой сайта hallizar.ru

Стек проекта: **Astro (статическая генерация) + React + Tailwind**, CMS **Decap CMS** (бывш. Netlify CMS),
деплой через **GitHub Actions → GitHub Pages**, домен — **reg.ru**.

---

## 1. Как пользоваться сайтом (для автора/владельца)

### 1.1. Локальный запуск для разработки

```bash
# Установка зависимостей
npm install

# Запуск dev-сервера (http://localhost:3000)
npm run dev

# Сборка статической версии в папку dist/
npm run build

# Проверки типов и сборки
npm run lint
npm run verify:build
```

Переменные окружения (например, `GEMINI_API_KEY`) копируются из `.env.example` в `.env`.
Файл `.env` **нельзя** коммитить в Git.

### 1.2. Структура проекта

| Путь | Назначение |
|---|---|
| `src/content/posts/` | Статьи блога (Markdown с frontmatter) |
| `src/content/ads/` | Рекламные кампании (баннеры, RTB) |
| `src/pages/blog/` | Роуты блога (`index.astro`, `[slug].astro`) |
| `src/components/`, `src/layouts/` | UI-компоненты и шаблоны страниц |
| `public/admin/` | Панель Decap CMS (`config.yml` — настройки модерации) |
| `public/assets/` | Статика: изображения, загрузки медиа |
| `public/CNAME` | Привязка домена hallizar.ru к GitHub Pages |
| `.github/workflows/deploy.yml` | CI/CD: автосборка и публикация на GitHub Pages |

### 1.3. Публикация статьи без CMS (через Git)

1. Создайте файл `src/content/posts/имя-статьи.md`.
2. Добавьте frontmatter (поля должны совпадать со схемой в `public/admin/config.yml`):

```markdown
---
title: "Заголовок статьи"
date: 2026-10-02T12:00:00+03:00
description: "Краткое SEO-описание"
category: "Технологии"
draft: false
---

Текст статьи в Markdown…
```

3. Коммит и push в `main` — GitHub Actions автоматически пересоберёт сайт:

```bash
git add src/content/posts/имя-статьи.md
git commit -m "feat: новая статья"
git push origin main
```

## 2. Как модерировать сайт (Decap CMS)

### 2.1. Вход в панель

- Откройте `https://hallizar.ru/admin/`
- Нажмите **Login with GitHub** и авторизуйтесь аккаунтом, который добавлен в репозиторий.

### 2.2. Права доступа (кто может модерировать)

CMS пишет изменения напрямую в GitHub-репозиторий (`backend: github`, ветка `main`).
Поэтому доступ к редактированию = доступ к репозиторию:

- **Полный доступ (push):** владелец репо или Collaborator с ролью Write.
- **Только предложения:** пользователь без прав push — CMS создаст **Fork + Pull Request**,
  который владелец должен одобрить и смержить (это и есть режим модерации).

Добавить сомодератора: `Settings → Collaborators and teams → Add people`.

### 2.3. Рабочий процесс модерации

1. **Work in Progress (WIP):** черновики видны только вам; кнопка *Publish* ставит статью в очередь.
2. **Review Workflow:** при включённом moderation (см. п. 2.4) публикации попадают в PR со статусом
   In Review / Ready for Review. Модератор открывает вкладку **Editorial Workflow** (иконка доски)
   и переводит карточки между колонками, комментирует или отклоняет.
3. **Медиа:** загружайте изображения через Media Library — они сохранятся в
   `public/assets/uploads` (поле `media_folder` в config.yml).
4. **Реклама:** коллекция Ads позволяет включать/выключать кампании (`Active`), задавать
   даты старта/окончания, приоритет ротации и ID блока Яндекс RSAC/RTB.
5. После merge PR в `main` GitHub Actions пересобирает и публикует сайт — вручную ничего деплоить не нужно.

### 2.4. Включение review-очереди (опционально)

В `public/admin/config.yml` добавьте:

```yaml
publish_mode: editorial_workflow
```

Тогда ни одна публикация не попадёт на сайт без одобрения через Pull Request.

### 2.5. Тестирование CMS локально

```bash
npx decap-server   # поднимет local_backend на http://localhost:8081
npm run dev
```

Откройте `http://localhost:3000/admin/` — CMS будет писать файлы прямо в рабочую директорию,
без GitHub-логина.

### 2.6. Правила контента (чек-лист модератора)

- Уникальность и фактическая точность; без плагиата и запрещённой рекламы.
- Обязательны: `title`, `description` (SEO/OpenGraph), корректная `date`, обложка.
- Ссылки в рекламе — только полные `https://…` (валидируется widget `pattern`).
- Для зоны .RU/.РФ: соответствие 152-ФЗ (согласие на обработку ПДн), маркировка
  интернет-рекламы (erid / RSAC) для баннеров из коллекции Ads.
- Перед публикацией крупного контента убеждайтесь, что CI-сборка зелёная
  (локально: `npm run verify:build`).

## 3. Деплой через GitHub Pages

CI уже настроен в `.github/workflows/deploy.yml`: push в `main` → сборка `npm run build`
→ публикация содержимого `dist/` на GitHub Pages.

### 3.1. Разовая настройка репозитория

1. Репозиторий должен быть **публичным** (или Pages на платном тарифе).
2. GitHub → `Settings → Pages → Source: Deploy from a branch` — сам workflow публикует
   артефакт через `actions/upload-pages-artifact` + `actions/deploy-pages`, отдельно
   настраивать ветку gh-pages не нужно.
3. Убедитесь, что в `astro.config.mjs` стоит `site: 'https://hallizar.ru'`.
   (Если публикуете в подпапку вида `username.github.io/repo`, добавьте `base: '/repo'`.)

### 3.2. Обычный деплой

```bash
git push origin main   # этого достаточно — Actions соберёт и опубликует сайт
```

### 3.3. Ручной запуск деплоя

GitHub → `Actions → Deploy to GitHub Pages → Run workflow` (кнопка *Run workflow*,
workflow поддерживает `workflow_dispatch`).

### 3.4. Проверка

Через 1–3 минуты сайт доступен по адресу из вкладки Actions (или по домену из CNAME).
Если сборка упала — сайт остался на предыдущей версии; смотрите логи в **Actions**.

## 4. Подключение домена reg.ru к GitHub Pages

### 4.1. GitHub-сторона

1. Файл `public/CNAME` содержит `hallizar.ru` и попадает в `dist/` при каждой сборке.
   Дополнительно закрепите домен в настройках:
   `Settings → Pages → Custom domain → hallizar.ru → Save` и включите **Enforce HTTPS**.
2. IP-адреса GitHub Pages (получить: `dig +short <username>.github.io`):

```
185.199.108.153
185.199.109.153
185.199.110.153
185.199.111.153
```

### 4.2. Конструктор сайтов reg.ru vs собственный репозиторий

⚠️ Если сайт собран в **конструкторе reg.ru**, деплой происходит самой платформой reg.ru
(редактор → «Опубликовать»), а GitHub Pages не используется. Ниже — вариант для
**собственного кода с GitHub Pages** (ваш случай, судя по репозиторию).

### 4.3. reg.ru — настройка DNS

0. Сначала убедитесь, что домен обслуживается NS-серверами reg.ru:
   выполните в терминале `nslookup -type=NS hallizar.ru`. Если в ответе
   серверы вида `ns1.reg.ru` / `ns2.reg.ru` — всё в порядке, переходите к п. 1.
   Если NS сторонние (например, хостинга или Cloudflare) — сначала в кабинете:
   **Домены и DNS → hallizar.ru → «Управление DNS-серверами»** → выберите
   «NS-серверы REG.RU» (сохранятся только после смены, распространение до 24 ч).

1. Личный кабинет reg.ru → **Домены и DNS** → выберите `hallizar.ru` →
   **Управление DNS-зоной** («Изменить DNS-записи»).
2. В форме добавления записи **имя домена (Host) для корневых A-записей
   оставляйте пустым** (или ставьте `@`) — reg.ru может не принимать `www`
   в A-записи и требует, чтобы корень задавался без имени.
3. Добавьте/измените записи:

| Тип | Имя (Host) | Значение | TTL |
|---|---|---|---|
| A | `@` (пусто) | `185.199.108.153` | 600 |
| A | `@` | `185.199.109.153` | 600 |
| A | `@` | `185.199.110.153` | 600 |
| A | `@` | `185.199.111.153` | 600 |
| AAAA | `@` | `2606:50c0:8000::153`…`2606:50c0:8003::153` (опционально) | 600 |
| CNAME | `www` | `hallizar.ru` (или `<username>.github.io`) | 3600 |

❗ Удалите конфликтующие записи: любой другой `A @` или `CNAME @`.
MX-записи почты reg.ru не трогайте.

4. Сохраните. Обновление DNS — от нескольких минут до ~24 часов
   (проверка: `dig hallizar.ru A`, `nslookup www.hallizar.ru`).

### 4.4. SSL-сертификат

GitHub автоматически выпустит сертификат Let's Encrypt после того, как DNS начнёт
резолвиться на его IP. Пока сертификат не готов, Pages покажет «Certificate not yet
issued» — подождите и обновите. Включите **Enforce HTTPS** в `Settings → Pages`.

### 4.5. Требования для зоны .RU/.РФ

- Актуальные данные владельца в WHOIS.
- Страница о владельце домена (обычно формируется reg.ru автоматически).
- Маркировка интернет-рекламы (erid/RSAC) для баннеров; отсутствие запрещённого контента.

### 4.6. Быстрая проверка связки

```bash
curl -I https://hallizar.ru          # ожидаем HTTP 200 и Server: GitHub.com
curl -I https://hallizar.ru/admin/   # панель CMS отвечает 200
dig +short hallizar.ru               # возвращает 185.199.1xx.153
```

## 5. Типичные проблемы (Troubleshooting)

| Симптом | Причина / решение |
|---|---|
| Push есть, сайт не обновился | Вкладка Actions: сборка красная? Смотрите лог шага `Build static site`; часто — ошибки типов (локально `npm run lint`). |
| «DNS records are not valid» | Осталась старая A-запись / конфликтующий CNAME; подождите распространение DNS. |
| HTTPS не работает | Подождите выпуска сертификата (до ~15 мин после смены DNS); включите Enforce HTTPS. |
| CMS не сохраняет | У пользователя нет прав Write на репо → создаётся PR: мержите его. Или истёк OAuth-токен — перезалогиньтесь. |
| Блог-роуты отдают 404 | Workflow копирует `dist/index.html` в `404.html` как SPA-фолбэк; для чистых Astro-страниц это не требуется — проверьте, что страница реально сгенерирована в `dist/`. |
